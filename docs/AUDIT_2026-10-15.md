# Audyt techniczny TradingHelper — 2026-10-15

## Zakres i wynik

Przejrzano obsługę API i uwierzytelniania, SQLite i backupy, dostawcę danych, retry i
cache, harmonogram oraz skanowanie, odczyt cen OCR, frontendowy service worker, testy i
instrukcje operacyjne. Zweryfikowano też bieżące, niezacommitowane zmiany w repozytorium.
Audyt bezpieczeństwa oraz niezawodności wykonano niezależnie, a poprawki i integrację
prowadził główny agent.

Znaleziono 14 problemów: **13 poprawiono**, a wzrost historii bazy pozostawiono jako
jawne ograniczenie, ponieważ automatyczne kasowanie migawków portfela i dziennika
zdarzeń mogłoby nieodwracalnie usunąć dane. Nie znaleziono SQL injection w sprawdzonych
trasach; zapytania korzystają z parametrów. Nie wykryto permissive CORS. Bind domyślny
pozostaje lokalny, a dla dostępu zdalnego aplikacja wymaga włączonego auth.

## Zabezpieczenia i dane

Sesje są losowe, przechowywane w SQLite jako HMAC, cookie ma `HttpOnly` i `SameSite=Strict`,
a `Secure` jest ustawiane dla HTTPS. Nie stwierdzono permissive CORS ani nieparametryzowanych
zapytań w analizowanych trasach. Publiczne `/health` i `/ready` nie wymagają sesji, więc
nie zwracają danych portfela; `/ready` ujawnia jedynie ogólny stan bazy. Domyślny bind to
loopback, a `ensure_safe_bind` blokuje zdalny bind bez auth. Zdalny dostęp nadal wymaga
kontrolowanej sieci i HTTPS zgodnie z `SECURITY.md`.

Backup SQLite korzysta z online backup API, a nowa kopia przechodzi `integrity_check`.
Plik backupu nie jest szyfrowany; uprawnienia systemowe nie chronią przed kradzieżą dysku,
kontem administratora ani utratą całego hosta. Potrzebna jest szyfrowana kopia poza hostem.
Zdarzenia błędów providera i surowe wyjątki w innych ścieżkach należy okresowo przeglądać
pod kątem ujawniania danych przez przyszłe integracje.

## Weryfikacja i zasięg zmian

Dodano lub rozszerzono testy dla zakresów list API, trybów backupu i ujemnej retencji,
braku ponawiania błędów 4xx i retry 5xx, użycia krótkiej serii cache, współbieżnego skanu
oraz rozróżniania cen OCR. Po instalacji zależności w `.venv`:

- `.venv/bin/python -m pytest --ignore=tests/test_web_e2e.py` — **83 passed**.
- `.venv/bin/ruff check src tests` — **All checks passed**.
- `git diff --check` oraz `python3 -m compileall -q src tests` — bez błędów.
- Test fixture E2E nie otwiera już lokalnego portu: ruch strony jest przekazywany do
  aplikacji ASGI bezpośrednio w procesie testowym. Pełny `pytest` kończy się **83 passed,
  6 skipped**. E2E pomijają się, gdy w sandboxie nie można uruchomić systemowego Chrome;
  binarium Chromium Playwright nie jest dostępne dla tego hosta macOS 12.
- Kontrola wizualna wymaga uruchomienia `tests/test_web_e2e.py` poza sandboxem, gdzie
  Chrome może startować jako proces potomny.

FastAPI/Starlette zgłasza ostrzeżenie o planowanej zmianie integracji `httpx` w
`TestClient`; nie powoduje ono błędów testów jednostkowych.

Największy zasięg mają zmiany `api.py`, `service.py`, `market_data/cache.py`,
`market_data/resilience.py`, `market_data/twelve_data.py` i `screen_ocr.py`. Testy
automatyczne pokrywają logikę, ale nie zastępują rzeczywistego sprawdzenia dostępu do
ekranu macOS, limitów konta Twelve Data ani backupu na docelowym systemie plików.
